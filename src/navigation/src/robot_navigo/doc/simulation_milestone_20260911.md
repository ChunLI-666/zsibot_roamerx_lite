## 完整时间 plant

提交 `8ec79d3` 去掉 `min(wall_delta,0.1)`，按真实单调时钟结算全部时间。新命令和运动约束变更先结算旧命令；350ms 看门狗在积分区间内部到期停车，不再用回调末端状态代替整个区间。移动段按不超过 20ms 分段，使用精确恒定 body twist 积分，日志记录每段开始／结束单调时间。暂停 ROS 时间不会凭空瞬停物理运动。

新增 tick 各阶段 wall／thread CPU 耗时，区分 scan 计算和发布／调度停顿。该观测尚不能解释没有分段计时的旧 336ms 停顿。显式冻结 motion 仅供模拟阻塞和 BT 进展失败，并非真实碰撞接触模型。

### 自动恢复与动态场景

提交 `b534c2a` 完成四项实际链路修复：epoch 模式显式选取固定恢复树；已到达的动作终止结果优先于新路径；可恢复的 progress failure 封存旧执行令牌，保留健康任务的恢复流程；动作回调使用正 1ms 预算持续处理就绪队列，解决 20Hz 反馈让 ACK 长期排队的问题。保持原 2s 接受回执、6s BT 动作超时，未放宽控制时效和几何约束。恢复仍默认关闭，仅实验 overlay 显式开启。

旧令牌不能通过 active 或命令重放恢复授权。新 BACKUP 必须有更大请求序列，并通过当前定位身份、challenge、intent／execution 时效与实际安装校验。终止例外不能掩盖定位失效、身份切换、急停或 intent 断流；这些情况仍撤权。独立只读 policy review 未发现本次窄修改的阻塞安全问题。

### Gazebo 与 pd1

本地 Gazebo Sim 8／ROS Jazzy 已产出原始 LiDAR、IMU 和独立引擎真值。使用 ZSL-1 本地模型中的传感器资产构造隔离传感器架；雷达为 16×360、10Hz 的瞬时 GPU 扫描，IMU 为 100Hz。GT 单独保存，不输入建图／定位。输入适配使用已有 `lidar_type=5`、逐点时间跨度 0ms 和 SI 单位；不虚构 Livox 点时间。pd1、2.61 分数、1.5m 修正、三帧确认保持原设置。

原位静态链路曾提交进入 Tracking，但这只说明静态路径可运行。移动 VelocityControl 录制的 GT 行进 2.520m，LIO 却只移动约 0.022m，地图只有一个关键帧；两个冻结位置／朝向×两个噪声 seed 的四个查询均为 **0/4 正确提交、0 错误提交**。修正继承配置的 `imu_in_g=true` 为 SI 配置后，对同一 moving bag 的重建仍只有一个 KF；源码证明该选项只在 SLAM 在线回调转换，所以它不是此次离线失败已确认的原因。

进一步核查运动输入：VelocityControl 数据在 102.1–102.9s 的 GT 加速度为 0.1200m/s²，IMU 对应 ax 均值仅 0.00491m/s²，均值标准误 0.00943，存在运动／惯性数据不一致；尚不能断言这是 LIO 失败的唯一原因。

改用 Gazebo 原生受力驱动做独立 8s 传感器 smoke：6.27kg 质量、0.3135N 水平力，理论及 GT 加速度均为 0.0500m/s²，IMU 均值 0.05633、标准误 0.00351m/s²，差值约 1.8 个标准误。该结果支持受力模型的运动输入一致性，但恒力从开始即施加，没有静止 IMU 初始化前缀，**未将其作为定位成功证据**。

完整脚本、配置、实验与哈希以 `04a5b81` 提交于定位 feature 分支（base `f0f41f9`）。7 次采集的格式／时间／GT 隔离检查与 3 项传感器架契约测试通过，生产算法源码未改。详见 [Gazebo 与 pd1 报告](/home/charles/project/colcon_ws/src/lightning-lm/doc/pd1_gazebo_simulation_report_20260911.md)。

下一步使用静止初始化前缀加受力／停稳轨迹重新建图，再运行冻结位置查询；确认移动定位后才能把实际 pd1 连接到导航联合路线。目前两套验证仍分开，不宣称已经打通传感器→定位→规划→执行的完整 Gazebo 闭环。真实数据新增位置 0/9 的失败保留。
